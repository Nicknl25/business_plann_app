ITEM 2 -- THE COLLAPSE ARITHMETIC, ADVERSARIALLY
================================================================================
ANSWER TO VS'S QUESTION (b): revenue-weighting is RIGHT, and it is right for
the reason that matters -- it preserves the group's direct-cost DOLLARS.

  two lines, 249,600 and 124,800 of revenue at 0.48 and 0.71:
    group COGS before collapse   $208,416.00
    group COGS after  collapse   $208,428.48   (shared rate 0.5567)
    the delta is $12.48 -- the 4dp rounding of the stored rate, nothing else.
    a plain average (0.595) would land $14,352 away from the truth.
  at 200:1 weights: before $1,005,784.00, after $1,005,691.44, shared 0.4811.
    The shared rate sits on the big line because that is what "these two
    together cost what they cost" MEANS. The small line's own rate moves 22.9
    points, and that is the client's instruction being obeyed, not a defect.

ANSWER TO VS'S QUESTION (a): the missing-weight case is NOT the plain-average
fallback VS described, and it is a DEFECT.

  Plant sale weight 249,600 at 0.48; Hard goods sale unit_price null, so
  _cogs_line_revenue_weight returns None -> the zip contributes weight 0.0.
    shared rate = 0.48 EXACTLY.
  The client's stated 0.71 for the other line is not averaged in, not
  down-weighted -- it is DROPPED. total_weight > 0, so the documented plain-
  average branch never runs. The receipt says
    {'line_names': [both], 'cogs_percent': 0.48}
  which reads as a computed shared rate. Nothing in the receipt, the row or the
  log says a stated rate was discarded.
  RULING SHAPE: refuse. A collapse whose members do not all carry a weight
  should either ask, or fall back to the plain average across ALL members and
  SAY SO in the receipt. Silently dropping a rate the client stated out loud is
  the receipt-without-a-write class with the polarity reversed.

  The all-weights-absent case does fall back to a plain average (0.595 from
  0.48/0.71) and is also silent about having done so.

  Not a defect, checked: one rated member and one unrated propagates the rate
  to the unrated line, and the grouped receipt names both lines and the rate,
  so the client sees it.

    -> the tolerance is NOT too tight for real differential rounding, which is

      20.00 pts fail   |  1.00 pts fail

  READING: every STRUCTURAL defect -- the model reverting to a blend, a wrong
  total range, rates landing on the wrong lines, the split never arriving -- is
  caught by an order of magnitude or more. The only thing 0.5% lets through is
  a sub-half-point rate drift, which no client-facing number depends on and
  which is inside the range genuine 4dp/6dp rounding produces. Tightening it
  buys nothing and risks failing correct workbooks.

  ONE HONEST LIMIT, stated because it is not obvious: bullet 3 is an INTERNAL

  wrong lines would propagate consistently and reconcile. Which line got which
  rate is the ops assertion's job and the receipt's job, not bullet 3's.

B. "1%" IS STORED AS 100%.
   _clamp divides by 100 only when the value exceeds 1.0. A client saying a
   line is 1% sends cogs_percent=1 -> stored 1.0 -> that line's direct cost is
   100% of its revenue. "half a point" -> 0.5 -> 50%. Verified through the
   production door. It passes every artifact assertion (non-null, distinct), so
   nothing downstream catches it, and W3 shows bare numbers reach the door from
   ordinary sentences. Ravenwood's own design line was 4%; 1% is not exotic.
   FIX SHAPE: the unit must be declared, not inferred. Have the router emit the
   unit with the figure (or normalise to percent at the router, where the
   client's own words are still visible) and convert unconditionally at the
   door; refuse rather than guess when the unit is absent.

C. A CLIENT WHO DECLARES ONE RATE FOR EVERY LINE IS FILED AS A RECURRENCE.
   _assert_ops_per_line_cogs's own docstring says the all-share case "must opt
   out EXPLICITLY, from the recorded grouping" -- the code only reads
   spec['allow_shared_rates'], a probe-spec key nobody sets mid-run and that
   Nick would have to edit machinery to set. Measured:
     4 lines / 4 rates ............................ pass
     2 share + 2 differ (the declared collapse) ... pass
     ALL FOUR at 0.55, no group stored ............ FAIL "a blend wearing
                                                    per-line clothing"
     ALL FOUR at 0.55, group STORED on all four ... FAIL (same), while
                                                    ops_cogs_shared_group PASSES
   My live W3 shows a client reaches this state with one ordinary sentence.
   This is the false confirmation's mirror image: a false RECURRENCE, filed
   against a model that is exactly what the client asked for.
   FIX SHAPE: implement the docstring. When all rows share one rate, pass if a
   stored cogs_cost_structure_group covers every line (the client's own
   recorded authority), fail otherwise -- and have the door store that group
   when the client declares a single rate across all lines.

D. LATENT: AN UNNAMED PRODUCT ROW MATCHES ANY WORDING.
   _resolve_cogs_line's loose branch tests `product_name in target`, and ""
   is a substring of everything. A directory with exactly one unnamed row
   returns that row for ANY client phrasing: "the pavers side" wrote 0.71 onto
   the blank row and the receipt called it "Garden".
   CENSUS BEFORE YOU PANIC: 0 of 3,050 drafts carrying an ops model have any
   unnamed product row. This is latent, not live. Still worth the one-line
   guard -- skip entries with an empty product_name in the loose branch --
   because a door whose whole design is "refuse rather than guess" should not
   have a wildcard in it.
