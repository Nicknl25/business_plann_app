# P3.32 — Handler C prompt + SQL lookup table audit

**Status:** Read-only investigation. No code changes. No fixes proposed
without user review.
**Scope:** Diagnose why K8 enrichment (alternative-labor-intensity-class
suggestion in failure feedback) was empirically ignored by GPT on the
Skyward Express run, then scope the broader prompt-vs-lookup-table
architectural opportunity.

---

## §1 P1-P7 findings on Handler C prompt structure

Handler C is `estimate_payroll_headcount_schedule_with_gpt` at
[post_intake_headcount/schedule.py:2180](../../python/client_intake_and_finmo/post_intake_headcount/schedule.py#L2180).
The iterative refinement loop runs at lines 2448-2709.

### P1 — Bounds-vs-class binding

**The class-specific bound is enforced ONLY in post-response Python
validation, NOT in the OpenAI JSON schema.**

The OpenAI schema generated by `post_intake_gpt_contract_openai_schema`
([post_intake_mapping.py:9403](../../python/client_intake_and_finmo/post_intake_mapping.py#L9403))
emits the GLOBAL envelope for `target_payroll_percent_of_revenue`:

- SQL row (`post_intake_gpt_contract_lookup`, contract_name=
  `payroll_headcount_schedule`, field_path=
  `target_payroll_percent_of_revenue`):
  `min_value=0.060000, max_value=0.800000`
- This is the **union** of all four class bounds:
  - low: [0.06, 0.45]
  - medium: [0.10, 0.55]
  - high: [0.16, 0.70]
  - expert: [0.18, 0.80]

The per-class narrowing was historically encoded as JSON-schema
`allOf`/`if`-`then` branches but was REMOVED:

> [post_intake_mapping.py:3069-3078](../../python/client_intake_and_finmo/post_intake_mapping.py#L3069-L3078)
> "Phase 9 P3.13 Sunny fix #2 — OpenAI strict-mode JSON schema does
> NOT permit `allOf` (rejected with `invalid_json_schema`). The
> tier-conditional bounds previously added here as if/then branches
> are now enforced post-parse by the runtime validator
> `headcount_payroll_revenue_sanity_bounds`."

So today the class binding lives in TWO places only:

1. SQL `prompt_required_instruction` for the field (paraphrase only):
   > "Express as a decimal in [0.06, 0.80]... The selected
   > labor_intensity_class narrows this further via the tier bounds
   > in post_intake_headcount_policy_lookup.payroll_revenue_sanity_
   > bounds_json. This does not drive payroll math or force FTE."

2. `task_instruction` arg passed at
   [schedule.py:2566](../../python/client_intake_and_finmo/post_intake_headcount/schedule.py#L2566):
   > "target_payroll_percent_of_revenue is a decimal in [min_pct,
   > max_pct] for the chosen labor_intensity_class (e.g., for medium
   > intensity the band is 0.10..0.55)."

Note (1) and (2) both POINT GPT at the SQL table but do NOT contain
the actual bounds for every class. The example in (2) names only the
medium band. GPT receives the global [0.06, 0.80] envelope from the
strict-mode schema; everything narrower is prose.

**Implication:** GPT can produce any value in [0.06, 0.80] without
violating the strict schema. The class-binding violation surfaces
only when the post-response Python validator runs.

### P2 — Unit consistency

**Units ARE consistent across surfaces. NOT the issue.**

All surfaces express bounds as decimals:
- SQL schema min/max:
  [post_intake_gpt_contract_lookup](../../python/client_intake_and_finmo/post_intake_mapping.py)
  for target_payroll_percent_of_revenue → 0.060000 / 0.800000
- SQL `payroll_revenue_sanity_bounds_json` → `{"low": {"min_pct": 0.06,
  "max_pct": 0.45}, ...}` ([lookup.py:74-79](../../python/client_intake_and_finmo/post_intake_headcount/lookup.py#L74-L79))
- task_instruction example at
  [schedule.py:2566](../../python/client_intake_and_finmo/post_intake_headcount/schedule.py#L2566):
  "decimal in [min_pct, max_pct] (e.g., 0.10..0.55)"
- Explicit disambiguation at same line: "0.45 means 45 percent. Do
  NOT emit 45 (which would be 4500 percent) and do NOT emit 0.045
  (which would be 4.5 percent)."
- Validator emit code:
  [lookup.py:1048-1051](../../python/client_intake_and_finmo/post_intake_headcount/lookup.py#L1048-L1051)
  `payroll_headcount_target_payroll_percent_of_revenue_out_of_policy_range:value=0.105:min=0.16:max=0.7`
  (decimals)
- K8 enrichment ([schedule.py K8 block]) uses
  `{"labor_intensity_class": "low", "min_pct": 0.06, "max_pct": 0.45}`
  (decimals)

Skyward GPT empirically emitted decimals (0.105, 0.08) — never a
percent-scale value. P2 is NOT the root cause.

### P3 — Competing instructions (THIS IS THE KEY FINDING)

**The "revise ONLY the named fields" rule directly conflicts with
K8's alternative-class suggestion.**

At
[schedule.py:2510-2516](../../python/client_intake_and_finmo/post_intake_headcount/schedule.py#L2510-L2516),
the iterative refinement instruction in `previous_contract_failure
.required_action` reads:

> "Return a corrected full payroll_headcount_schedule. The structured
> failures below name the specific fields and constraints that
> tripped. **Revise ONLY the fields named in the failures; keep all
> other fields unchanged unless a structural cascade is required.**
> The iterative refinement system gives you up to 10 total rounds..."

And again at
[schedule.py:2569](../../python/client_intake_and_finmo/post_intake_headcount/schedule.py#L2569)
in the static task_instruction:

> "ITERATIVE REFINEMENT: If your initial plan fails validation, you
> will receive structured failures naming the field, the actual
> value, the required range, and the failure category. **Revise ONLY
> the fields named in the failures; keep all other fields unchanged
> unless a cascade is required.** You have up to 10 total rounds."

K8 surfaces alternative classes inside the FAILURE entry whose
`field` is `target_payroll_percent_of_revenue`. The failure does NOT
name `labor_intensity_class` as the broken field. So GPT, following
the "revise only named fields" rule, refuses to switch class — even
though K8 explicitly suggests doing so in the same failure's
`context.alternative_labor_intensity_classes_for_actual_value`.

K8's suggestion thus reads to GPT as INCONSISTENT WITH THE PROMPT
DIRECTIVE. GPT correctly applies the more-prominent system-level
directive. This is the root cause of empirical Skyward behavior.

### P4 — K8 enrichment positioning

**K8 is buried in user-message JSON; not promoted to system prompt.**

K8's enrichment lives at:

  request_context
    .previous_contract_failure
      .translated_failures[N]
        .context
          .alternative_labor_intensity_classes_for_actual_value

The full request_context is dumped to the **user message** as JSON
([schedule.py:2574-2577](../../python/client_intake_and_finmo/post_intake_headcount/schedule.py#L2574-L2577)):

```python
payload["input"] = [
  {"role": "system", "content": [{"type": "input_text", "text": system_prompt}]},
  {"role": "user", "content": [{"type": "input_text", "text": json.dumps(request_context, ensure_ascii=False)}]},
]
```

So the K8 alternative is 5+ JSON levels deep in the user message,
AFTER the more-prominent `previous_contract_failure.required_action`
text (which says "revise ONLY the named fields"). The system prompt
itself never mentions class-switching as a remediation path.

LLM attention is documented to favor system-prompt content and
text-block content over deeply-nested JSON. K8's position works
AGAINST visibility.

### P5 — Class mutability framing

**The prompt frames class as effectively IMMUTABLE after Round 1.**

Round 1 task_instruction at
[schedule.py:2544](../../python/client_intake_and_finmo/post_intake_headcount/schedule.py#L2544):

> "**First choose** capacity_labor_model, labor_intensity_class,
> wage_positioning_tier, wage_positioning_multiplier,
> target_payroll_percent_of_revenue, and capacity_units_per_supporting_fte
> from payroll_decision_options where enumerated..."

"First choose" implies a one-time decision. Combined with P3's
"revise ONLY the named fields" rule for subsequent rounds, the
operational semantics are: class is chosen at Round 1 and stays
fixed unless a future failure names `labor_intensity_class` as the
broken field.

K8's class-switching invitation has no prompt-level override that
would suspend the "revise only named fields" rule when an
alternative class exists.

### P6 — Rationale-vs-structured alignment mechanism

**NO self-check mechanism in the prompt.**

The schema enforces the structured output's TYPE and ENVELOPE but
not its INTERNAL CONSISTENCY with rationale text. The prompt does
not ask GPT to:
- Verify its `target_payroll_percent_of_revenue` falls in the bounds
  for its chosen `labor_intensity_class` before submitting
- Quote the chosen value AND the binding class in the rationale
  text
- Re-check the rationale against the structured fields

Empirical Skyward evidence (round 10):

Rationale text:
> "Maintain the previously selected high labor-intensity operating
> model for a regional airline and adjust only the target payroll
> percent of revenue **into the required policy band**, keeping the
> existing supporting staff mix..."

Structured fields:
- labor_intensity_class: "high"
- target_payroll_percent_of_revenue: **0.08** (BELOW high.min_pct=0.16)

GPT's rationale claims it adjusted INTO the band; the structured
field is BELOW the band. Without a self-check, GPT generates
plausible rationale prose independent of structured field values.
This is the canonical P3.23a drift pattern.

### P7 — Feedback packet structure across rounds

**REPLACE-only feedback. GPT cannot see its own pattern.**

Each round at
[schedule.py:2681-2685](../../python/client_intake_and_finmo/post_intake_headcount/schedule.py#L2681-L2685):

```python
last_failure_packet = _build_payroll_iterative_feedback_packet(
  exc=exc,
  parsed=parsed,
  round_n=round_n,
)
```

`last_failure_packet` is OVERWRITTEN per round. The next round sees
ONLY the most recent failure. There is no accumulated history.

Operational consequence: at round 10, GPT cannot see that rounds
3, 5, 7, and 9 all produced the same (class=high, target≈0.10)
pattern — only the round 9 failure. GPT has no signal that its
strategy is stuck in a loop.

## §2 L1-L4 findings on SQL lookup table opportunity

### L1 — Policy data currently embedded as prompt text

The per-class payroll_revenue_sanity_bounds are PRESENT in SQL but
PARAPHRASED INTO PROMPT prose. Concretely:

- SQL table `post_intake_headcount_policy_lookup`, column
  `payroll_revenue_sanity_bounds_json`, policy_code=default:
  `{"low":{"min_pct":0.06,"max_pct":0.45},"medium":{"min_pct":0.1,"max_pct":0.55},"high":{"min_pct":0.16,"max_pct":0.7},"expert":{"min_pct":0.18,"max_pct":0.8}}`

- This SQL data is read at validation time by
  `headcount_payroll_revenue_sanity_bounds`
  ([lookup.py:836](../../python/client_intake_and_finmo/post_intake_headcount/lookup.py#L836)).
  GPT NEVER sees this directly.

- GPT sees only:
  - SQL contract `prompt_required_instruction`:
    "The selected labor_intensity_class narrows this further via
     the tier bounds in post_intake_headcount_policy_lookup.payroll
     _revenue_sanity_bounds_json."
  - task_instruction example at schedule.py:2566:
    "for medium intensity the band is 0.10..0.55"

So GPT receives a POINTER ("look at SQL X") and ONE example
(medium=0.10..0.55) but is expected to KNOW all four class bounds
from training data. This is a structural prose-paraphrase pattern.

Similar prose-paraphrase patterns for other policy fields:
- `wage_positioning_multiplier` bounds per tier
  (SQL: `wage_positioning_multiplier` JSON column;
  prompt: "Must be inside post_intake_headcount_policy_lookup.wage
  _positioning_multiplier bounds for the selected wage_positioning_
  tier" with no enumerated bounds)
- `capacity_units_per_supporting_fte`
  (SQL: lookup_source=post_intake_headcount_policy_lookup;
  prompt: "Python does not reject it using fake universal capacity-
  per-FTE reasonableness bounds")

### L3 — OpenAI function/tool-calling opportunity

**Tool-calling IS supported in the codebase by other handlers, but
NOT used by Handler C.**

Handler C's OpenAI payload at
[schedule.py:2417-2430](../../python/client_intake_and_finmo/post_intake_headcount/schedule.py#L2417-L2430):

```python
payload_base = {
  "model": _openai_model(),
  "temperature": 0,
  "text": {
    "format": {
      "type": "json_schema",
      "name": PAYROLL_HEADCOUNT_CONTRACT_NAME,
      "schema": post_intake_gpt_contract_openai_schema(...),
      "strict": True,
    }
  }
}
```

The payload uses `text.format.type=json_schema` (strict mode
structured outputs) with NO `tools` field. GPT cannot make function
calls.

In contrast, the GPT exhaustion handler uses tool-calling:

[post_intake_gpt_exhaustion_handler/tool_calling_session.py:205,544](../../python/client_intake_and_finmo/post_intake_gpt_exhaustion_handler/tool_calling_session.py#L205):
```python
# Line 205: "type": "function"
# Line 544: tools=[tool_def]
```

The pattern: define a function (compute_full_trajectory), GPT must
call it iteratively, the call result becomes input to GPT's next
turn. The funding handler uses the same pattern.

**The opportunity:** Handler C could expose tools like:

```
get_payroll_revenue_sanity_bounds(class) → {
  "labor_intensity_class": "high",
  "min_pct": 0.16,
  "max_pct": 0.70,
  "naics_sector": "481"
}

get_wage_positioning_multiplier_bounds(tier) → {
  "wage_positioning_tier": "market",
  "min": 1.0,
  "max": 1.5
}

list_alternative_intensity_classes_for_value(target_pct) → [
  {"labor_intensity_class": "low", "min_pct": 0.06, "max_pct": 0.45},
  {"labor_intensity_class": "medium", "min_pct": 0.10, "max_pct": 0.55}
]
```

GPT would be required (via tool_choice="required" or via system
prompt) to call `get_payroll_revenue_sanity_bounds(chosen_class)`
BEFORE producing target_payroll_percent_of_revenue. The structured
tool response makes the constraint impossible to miss; the
authoritative SQL data flows directly into GPT's context as a
function-call result, not as paraphrased prose.

### L4 — Architectural implications

If lookup-table-by-reference is adopted:

**Migration candidates** (highest-value first):
1. `payroll_revenue_sanity_bounds_json` per class (THE Skyward
   issue)
2. `wage_positioning_multiplier_json` per tier
3. `payroll_decision_options` (already provided in context but as
   prose JSON, could become a tool)
4. OEWS title catalog filtering (currently dumped in user message)
5. Realism band thresholds for the GPT exhaustion handler's
   bounds resolution (different handler but same pattern)

**Scope estimate for Handler C migration only:**
- Add tool definitions (~30 LOC): 2-3 function specs + JSON Schema
  for each
- Add tool-call handler that resolves SQL lookups (~50 LOC):
  dispatcher that maps function name → SQL query → response JSON
- Refactor Handler C's payload_base to include `tools` (~10 LOC) +
  potentially set `tool_choice="required"` for at least one tool
- Refactor the iterative refinement loop to handle multi-turn
  tool calls within a single round (~60 LOC): each round may now
  involve multiple tool-call/tool-result/final-response turns
- Adjust prompt to instruct GPT on when to call tools (~20 LOC)
- Tests for tool definitions, dispatcher, refactored loop (~80 LOC)

Total: **~250 LOC** for Handler C alone.

**Risk:**
- Tool-calling adds latency (extra round-trip per tool call)
- Doctrine impact: existing iterative refinement budget (180s) was
  sized for direct JSON output rounds; tool calls add overhead.
- Existing tests assume structured-output-only response shape.
- Conditional schema validation (allOf/if-then) STILL impossible
  in strict mode, so the post-response Python validator still has
  to run. Tool-calling reduces the GPT-error rate but doesn't
  eliminate the Python validator.

## §3 Diagnosis of why K8 enrichment failed

**Primary cause: P3 (competing instructions).**

The prompt directive at schedule.py:2513-2514 + 2569 says GPT must
"Revise ONLY the fields named in the failures." K8's enrichment
appears INSIDE a failure whose `field` is
`target_payroll_percent_of_revenue` — not `labor_intensity_class`.
GPT correctly applies the prominent directive: revise only the
named field. The class stays. The value moves but cannot reach the
bound for the unchanged class.

**Secondary causes that compound the failure:**

- **P4 (positioning):** K8's enrichment is buried 5 levels deep
  in a user-message JSON dump, after the more-prominent
  required_action text. LLMs preferentially attend to system
  prompt and top-level text content.
- **P5 (mutability framing):** "First choose" + "revise only
  named" together frame class as immutable. K8 has no
  prompt-level override that would suspend this rule.
- **P6 (no self-check):** GPT generates plausible rationale prose
  ("adjust into required band") that doesn't match the structured
  field (0.08 below the band). No mechanism forces alignment.
- **P7 (no history):** GPT can't see that rounds 3, 5, 7, 9 all
  produced the same pattern. Each round looks like a fresh
  problem; GPT has no signal it is stuck.

The K8 architectural intent was correct (give GPT the alternative
classes); the architectural placement was wrong (buried under a
contradicting directive).

## §4 Recommended fix shape

**TWO STAGES, ascending architectural ambition.**

### Stage A — Prompt restructure (~30-60 LOC)

This stage RESOLVES the Skyward failure without new SQL surfaces
or tool-calling infrastructure. It just makes K8's enrichment
visible and authoritative to GPT.

1. **Promote K8 enrichment to system-prompt level when present.**
   When the failure packet has `alternative_labor_intensity_classes
   _for_actual_value`, prepend a high-priority directive to the
   system prompt:
   > "OVERRIDE: The most recent failure has alternative labor_
   > intensity_class options that accept your current
   > target_payroll_percent_of_revenue value. You MAY (and
   > probably should) switch to one of those classes instead of
   > re-trying the same class. Specifically: [list]. The 'revise
   > only named fields' rule does NOT apply when a clean class
   > switch resolves the failure."
   This resolves P3 (competing instructions) and P4 (positioning).

2. **Add a rationale-vs-structured self-check directive.**
   Add to system prompt:
   > "Before submitting, verify that your chosen
   > target_payroll_percent_of_revenue value falls within the
   > min/max bounds for your chosen labor_intensity_class. If they
   > don't agree, either change the value to fit the class OR
   > change the class to fit the value. Your structured field
   > MUST match your rationale; if your rationale says 'I moved
   > to 20%', the field must read 0.20, not 0.08."
   Resolves P6.

3. **Accumulate failure history (or summarize the pattern).**
   Modify the per-round feedback packet to include a compact
   summary of prior rounds:
   > "Rounds 1-9 each produced (class=high, target≈0.10).
   > Validator rejected each. The pattern indicates a stuck
   > strategy; consider class switch."
   Resolves P7.

**Risk:** Low. Prompt-level changes only; existing structured
output schema unchanged; existing Python validators unchanged;
existing iterative refinement loop structure unchanged.
**Scope:** ~30-60 LOC across schedule.py.

### Stage B — Tool-calling migration (~250 LOC)

This stage addresses the L3 architectural opportunity. It removes
prose-paraphrased policy bounds in favor of SQL-canonical
function-call responses.

1. Define 2-3 tool functions Handler C exposes to GPT (Stage A's
   inline list becomes a tool call result).
2. Refactor iterative refinement to handle multi-turn (tool call,
   tool result, final response) within a single round.
3. `tool_choice="required"` to force at least one tool call per
   round before structured output.
4. Adjust prompt to reference the tools.

**Risk:** Medium. New tool infrastructure for Handler C; multi-turn
loop adds complexity; latency increase per round.
**Scope:** ~250 LOC.

**Sequencing recommendation:**
- Stage A first. Validates whether prompt-level fixes resolve
  Skyward (and likely other large-revenue drafts) without the
  architectural investment.
- Stage B if Stage A leaves residual cases OR if other similar
  prose-vs-table patterns surface in subsequent sweep iterations.
